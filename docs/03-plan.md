# Plan — Bardak

Главный линейный план разработки продукта. Мы не ведём отдельный план первой версии: продукт строится полноценно, но маленькими слоями, каждый из которых можно проверить, выпустить и расширить без переписывания основы.

Текущий фокус: **Telegram-бот, core data layer, тестируемые bot-flow**.

---

## Как пользоваться планом

Для каждого этапа фиксируем:

- **Цель:** какую пользовательскую или техническую ценность закрываем.
- **Решения:** что считаем выбранным, чтобы не возвращаться к этому в каждой задаче.
- **Работы:** конкретные шаги реализации.
- **Тесты:** что должно проверяться автоматически.
- **DoD:** условия, при которых этап считается закрытым.

Правило движения: не начинать следующий большой слой, пока текущий слой не имеет понятного DoD, тестов для критичной логики и обновлённой документации.

Глобальные правила:

- имена держим короткими: одно слово, если ясно; два-три слова только когда нужно;
- текущие `users`/bot implementation считаем черновиком, а не архитектурным ограничением;
- двигаемся vertical slices: быстро до рабочего поведения, но с тестами для критичной логики и расширяемой схемой.

## Этап 2. Core data model: entries, tags, links

**Цель:** заложить схему, которая позволит сохранять текст, ручные описания медиа, теги, входящие и будущие расширения без переписывания.

**Решения:**

- Материалы хранятся в таблице `entries`.
- Теги хранятся в таблице `tags` и создаются пользователем самостоятельно.
- Связь `entries` ↔ `tags` хранится отдельно в `entryTags`.
- Временные ожидания пользователя хранятся в `flows`.
- Один пользователь в одном чате имеет максимум один активный `flow`.
- У материала есть статус: `inbox`, `saved`, `archived`.
- `inbox` значит “уже сохранено, но лежит во входящих”, а не “не завершено”.
- `saved` значит “обычный материал вне входящих”.
- Несколько тегов на один материал должны поддерживаться схемой сразу.
- В продукте теги имеют hashtag-формат: `#example`, `#покупки`, `#project_ideas`.
- `#` не хранится в базе: `name` и `slug` сохраняются без решётки.
- V1 tag token: начинается с `#`, не содержит пробелов, поддерживает буквы, цифры и `_`.
- `kind` v1: `text`, `link`, `photo`, `voice`, `audio`, `document`, `video`, `sticker`, `unsupported`.
- Forwarded/reply — metadata/context, а не отдельные `kind`.

**Работы:**

- [x] Прочитать `apps/web/convex/_generated/ai/guidelines.md`.
- [x] Добавить таблицу `entries`.
- [x] Добавить таблицу `tags`.
- [x] Добавить таблицу `entryTags`.
- [x] Добавить таблицу `flows`.
- [x] Добавить таблицу `botEvents` для простого журнала активности бота.
- [x] Добавить индексы для idempotency, входящих, тегов, статусов и списка flows.
- [x] Добавить Convex mutations для сохранения материалов и тегов.
- [x] Добавить Convex mutation для записи bot events.
- [x] Добавить Convex queries для списка тегов и одного inbox item.
- [x] Обновить db meta/codegen.

**Тесты:**

- повторный `sourceChatId + sourceMessageId + userId` не создаёт дубль;
- тег с одинаковым slug не дублируется у одного пользователя;
- одна запись может иметь несколько тегов через `entryTags`;
- `#` не сохраняется в `tags.name` и `tags.slug`;
- запись без тега получает `status: 'inbox'`;
- запись с тегом получает `status: 'saved'`;
- пользователь не получает больше одного активного `flow` в одном чате.
- bot event сохраняет actor/source/action/status/context и читается через индекс.

**DoD:**

- [x] Convex schema синхронизируется без ошибок.
- [x] Все новые публичные функции имеют validators и return validators.
- [x] Индексы покрывают запросы без `filter()`.
- [x] Схема поддерживает текст, ссылки, ручные описания медиа и будущие AI-описания.
- [x] Bot events доступны в db admin registry.

## Этап 3. Text capture loop

**Цель:** пользователь отправляет текст боту, а Bardak сохраняет его как материал и запускает тегирование.

- Первый UX добавляет теги по одному, но позволяет выбрать `Добавить ещё тег` или `Готово`.

- [x] Создавать `flow: 'tag'` для сообщения без тега.

**Тесты:**

## Этап 6. Message types beyond text

**Цель:** начать принимать разные Telegram message types без обязательной автоматической AI-обработки.

**Решения:**

- Если у сообщения есть текст/caption, используем его как первичное описание.
- Если текста нет, бот сохраняет metadata, оставляет материал `inbox` и просит ручное описание.
- Для фото, voice, audio, document, video и sticker храним Telegram metadata и `fileId`, если доступен.
- Unsupported message сохраняется как `kind: 'unsupported'`, `status: 'inbox'`, с metadata и просьбой дать описание.
- `edited_message` и удаление Telegram-сообщений в v1 не синхронизируются.
- AI-описания и транскрибация подключаются позже как enrichment, а не как обязательный ingestion.

- пользователь без оплаты не теряет уже сохранённые данные.
- неверная подпись provider callback отклоняется;
- отменённая или незавершённая оплата не выдаёт Pro.

**DoD:**

- [ ] Можно принять оплату через YooMoney/U-Money и выдать доступ.
- [ ] Лимиты не превращаются в риск потери данных.
- [ ] Payment provider можно заменить без переписывания core entitlement logic.

## Этап 12. Web cabinet

**Цель:** дать пользователю удобный второй интерфейс для просмотра, фильтрации и редактирования базы.

**Решения:**

- Web не заменяет бота, а работает поверх тех же Convex-сущностей.
- Авторизация строится вокруг Telegram Login Widget или Telegram WebApp initData.
- Web не создаёт отдельную модель тегов, страниц или материалов.
- Web учитывает `entitlements`, но не содержит provider-specific payment logic.

**Работы:**

- [ ] Авторизация через Telegram.
- [ ] Лента сохранённых материалов.
- [ ] Фильтры по тегам и типам.
- [ ] Детальный просмотр материала.
- [ ] Управление тегами.
- [ ] Редактирование страниц: заголовок, описание, порядок.
- [ ] Экран тарифа и лимитов.
- [ ] Настройки аккаунта и privacy mode.

**Тесты:**

- пользователь видит только свои материалы;
- фильтры не используют неиндексируемые full scans;
- публичные страницы не требуют авторизации, приватные данные требуют;
- тарифные ограничения читаются из `entitlements`;
- privacy settings не ломают bot-flow.

**DoD:**

- [ ] Через web можно просмотреть и отредактировать основную базу.
- [ ] Web не дублирует бизнес-логику бота.

## Этап 13. External web integration

**Цель:** подключить внешний web-интерфейс/приложение как отдельный клиент поверх той же базы Bardak, не создавая вторую модель данных.

**Решения:**

- Интеграция не заменяет `apps/web`, а является отдельным клиентским слоем.
- Источник истины остаётся в Convex: `users`, `entries`, `tags`, `entryTags`, `pages`, `entitlements`.
- Auth/handshake проектируется отдельно от Telegram bot-flow.
- Внешний клиент не получает прямой доступ к чужим материалам и не обходит ownership checks.
- Название и конкретный протокол интеграции фиксируются перед реализацией, когда будет понятен xgas-side contract.

**Работы:**

- [ ] Зафиксировать contract внешнего web-приложения: какие экраны, данные и действия ему нужны.
- [ ] Спроектировать auth/handshake: Telegram identity, short-lived token или signed session.
- [ ] Добавить минимальные Convex queries/mutations для внешнего клиента.
- [ ] Добавить CORS/origin/env настройки, если клиент живёт отдельно.
- [ ] Добавить read-only сценарии: список entries, фильтры по tags, просмотр entry.
- [ ] Добавить write-сценарии только после read-only слоя: редактирование тегов, статуса и страниц.
- [ ] Описать manual smoke checklist для внешнего клиента.

**Тесты:**

- внешний клиент видит только материалы своего пользователя;
- token/session нельзя использовать для другого пользователя;
- read queries работают по индексам и bounded pagination;
- write mutations проверяют ownership на уровне Convex;
- отсутствие внешней интеграции не ломает Telegram bot-flow.

**DoD:**

- [ ] Внешнее web-приложение может безопасно читать базовые данные Bardak.
- [ ] Интеграция не дублирует core data model.
- [ ] Auth и ownership проверены тестами и smoke checklist.

## Вопросы и выбранные ответы

**Нужно ли хранить текст сообщений?** Да. Без хранения текста невозможны нормальный поиск, inbox preview и web-просмотр. В первой версии текст и описания хранятся в Convex без encryption; позже можно добавить privacy mode или encryption layer.

**Нужно ли хранить файлы?** Файлы не копируем в своё хранилище по умолчанию. Храним Telegram `file_id` и описание. Convex storage используем позже для превью или сгенерированных артефактов.

**Что делать с фото/голосовыми/файлами до AI?** Просить пользователя вручную описать материал несколькими словами. Это сразу делает материал searchable.

**Один тег или несколько?** Пользовательские теги не ограничены по количеству. Один материал может иметь несколько тегов через `entryTags`; первый UX добавляет их по одному через `Добавить ещё тег` / `Готово`.

**Как хранить hashtag-теги?** Пользователь вводит и видит теги как `#example`, но `#` не хранится в базе. `tags.name` и `tags.slug` содержат значение без решётки; Telegram-отображение добавляет `#` обратно.

**Что делать с сообщением без тега?** Сохранять как `inbox`, создавать `flow: 'tag'` и предлагать тег. Не терять сообщение из-за отсутствия тега.

**Как тестировать без Telegram?** Выносить normalizer/use-case logic из handlers и тестировать через fake input + fake Convex adapter. Для bot-flow и pure-логики сначала писать meaningful failing test, затем реализацию. Реальный Telegram остаётся smoke-тестом.

**Можно ли использовать `jose`/JWT для защиты содержимого?** JWT-подписи подходят для access-token signing, как в `proxy.ts`, но это не encryption содержимого. Шифрование текстов и описаний — будущий отдельный слой.

**Когда добавлять оплату?** После минимального bot-MVP: capture, tags, inbox, основные типы сообщений и базовый поиск. Первый планируемый provider — YooMoney/U-Money; доступ хранится как provider-independent `entitlements`.

**Когда добавлять внешнюю web-интеграцию?** После стабилизации core bot/data слоя и до полноценного web-кабинета, если внешний клиент уже нужен для реального использования. Интеграция должна читать и менять те же Convex-сущности, а не заводить параллельную базу.
