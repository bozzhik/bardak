# Telegram Bot — Bardak

Этот документ описывает текущий главный слой продукта: Telegram-бот. Он должен быть достаточно подробным, чтобы по нему можно было линейно реализовывать bot-flow, писать тесты и не возвращаться к одним и тем же вопросам.

---

## Роль бота

Бот — основной интерфейс Bardak.

Пользователь должен иметь возможность:

1. Отправить материал.
2. Быстро добавить тег или отложить сортировку.
3. Описать материал, если у него нет текста.
4. Найти сохранённое.
5. Позже собрать материалы в подборку.

Web и AI подключаются как усилители, но не как обязательные части первого core-flow.

---

## Режимы работы

Режимы реализуются по очереди:

| Режим                   | Статус        | Смысл                                                            |
| ----------------------- | ------------- | ---------------------------------------------------------------- |
| Личный чат с ботом      | текущий фокус | основной сценарий capture, tags, inbox и search                  |
| Приватная группа/канал  | позже         | пользователь хранит материалы в привычном групповом пространстве |
| Командный чат/workspace | позже         | несколько участников собирают общую базу и совместные подборки   |

Для текущей разработки все функции проектируются сначала для личного чата. Но нормализация Telegram-событий должна сохранять `chatId`, `chatKind`, `messageId` и author metadata, чтобы позже не переписывать ingestion под группы.

В первой рабочей версии бот не сохраняет материалы из групп. Если его добавили в группу или написали ему там, он коротко отвечает, что пока сохраняет только в личном чате.

---

## Принципы bot-flow

- **Сначала сохранить, потом уточнять.** Если это возможно, бот не должен терять материал только потому, что тег или описание не указаны сразу.
- **Inbox вместо блокировки.** Материал без тега или описания получает статус `inbox`, а в UX попадает во входящие.
- **Описание как searchable text.** Для фото, голосовых и файлов ручное описание пользователя является полноценным текстовым представлением материала.
- **Один lifecycle для всех типов.** Текст, фото, голосовое, документ и forwarded message должны проходить через общий entry lifecycle.
- **Тонкие handlers.** grammY handlers принимают update, вызывают нормализатор/use-case и отправляют reply.
- **Тестируемость без Telegram.** Основные решения принимаются pure-функциями и service-слоем.
- **Короткие имена.** В коде использовать минимально понятные имена: одно слово, если ясно; два-три слова только когда нужно.

## Основные сущности

### `users`

Хранит пользователя Bardak. Top-level поля оставляем для идентификации, индексов и частых выборок; редкие и расширяемые поля группируем.

Текущие поля:

| Поле         | Смысл                                             |
| ------------ | ------------------------------------------------- |
| `telegramId` | Telegram user id                                  |
| `username`   | Telegram username для быстрых админских сценариев |
| `botChatId`  | личный чат с ботом, если уже известен             |
| `webAuthId`  | будущая связь с web-auth                          |
| `status`     | `new`, `active`, `blocked`                        |
| `createdAt`  | timestamp создания                                |
| `updatedAt`  | timestamp последнего изменения                    |
| `lastSeenAt` | timestamp последнего контакта                     |
| `profile`    | Telegram profile fields                           |
| `settings`   | timezone/locale и будущие настройки               |
| `telegram`   | Telegram-specific state                           |
| `stats`      | счётчики событий                                  |
| `moderation` | blocked/unblocked metadata                        |

Решение: `entries`, `tags`, `entryTags` и `flows` ссылаются на `users._id`, а не на numeric Telegram id. `telegramId` нужен только для поиска/обновления пользователя по Telegram update.

### `entries`

Материал, который пользователь сохранил.

Текущие поля:

| Поле                | Смысл                                                                |
| ------------------- | -------------------------------------------------------------------- |
| `userId`            | ссылка на `users`                                                    |
| `source`            | пока `telegram`                                                      |
| `sourceChatId`      | Telegram chat id                                                     |
| `sourceMessageId`   | Telegram message id                                                  |
| `kind`              | `text`, `link`, `photo`, `voice`, `audio`, `document`, `video`, etc. |
| `status`            | `inbox`, `saved`, `archived`                                         |
| `text`              | основной searchable text                                             |
| `description`       | ручное или AI-описание для медиа/файлов                              |
| `descriptionSource` | `none`, `text`, `caption`, `user`, `ai`                              |
| `url`               | URL для link entry, если есть                                        |
| `telegram`          | сгруппированная Telegram metadata                                    |
| `createdAt`         | timestamp из mutation                                                |
| `updatedAt`         | timestamp из mutation                                                |

`kind` v1: `text`, `link`, `photo`, `voice`, `audio`, `document`, `video`, `sticker`, `unsupported`.

Forwarded/reply не являются отдельными `kind`: они хранятся как metadata/context поверх основного типа сообщения.

`telegram` хранит редкие и типоспецифичные поля, чтобы не раздувать top-level схему:

| Поле                       | Смысл                              |
| -------------------------- | ---------------------------------- |
| `telegram.type`            | исходный нормализованный тип       |
| `telegram.context`         | forward/reply metadata             |
| `telegram.file.fileId`     | Telegram file id, если есть        |
| `telegram.file.fileSize`   | размер файла, если Telegram отдаёт |
| `telegram.file.emoji`      | sticker emoji, если есть           |
| `telegram.file.setName`    | sticker set name, если есть        |
| `telegram.file.isAnimated` | sticker metadata, если есть        |
| `telegram.file.isVideo`    | sticker/video metadata, если есть  |

Решение: top-level поля оставляем для ownership, idempotency, статуса, поиска и частых сценариев. Telegram-specific metadata живёт внутри `telegram`.

### `tags`

Пользовательские hashtag-теги. Система не создаёт предзаданный список тегов.

Рекомендуемые поля:

| Поле        | Смысл                        |
| ----------- | ---------------------------- |
| `userId`    | владелец тега                |
| `name`      | исходный tag token без `#`   |
| `slug`      | нормализованный ключ без `#` |
| `createdAt` | timestamp                    |
| `updatedAt` | timestamp                    |

Правила v1:

- пользователь вводит и видит тег как `#example`;
- `#` не хранится в базе;
- tag token не содержит пробелов;
- разрешены буквы, цифры и `_`;
- количество тегов пользователя не ограничено на уровне продукта.

### `entryTags`

Связь многие-ко-многим между `entries` и `tags`.

Рекомендуемые поля:

| Поле        | Смысл          |
| ----------- | -------------- |
| `userId`    | владелец связи |
| `entryId`   | id материала   |
| `tagId`     | id тега        |
| `createdAt` | timestamp      |

### `flows`

Временное состояние диалога, когда следующий user input должен быть обработан не как новый entry, а как продолжение текущего flow.

Правило v1: один пользователь в одном чате имеет максимум один активный `flow`.

Рекомендуемые kinds:

| Kind          | Когда создаётся                                      |
| ------------- | ---------------------------------------------------- |
| `tag`         | entry сохранён без тега                              |
| `new_tag`     | пользователь выбрал создать новый тег                |
| `description` | media/file сохранён, но нужен searchable description |
| `search`      | пользователь начал поиск без query                   |

Текущая schema поддерживает `tag` и `description`. Остальные kinds добавляются отдельными slices, когда появится соответствующий flow.

## Entry lifecycle

```text
Telegram message
  -> normalize
  -> identify entry kind
  -> extract text/caption/url/file metadata
  -> save entry idempotently
  -> attach tag if known
  -> otherwise create flow
  -> reply with next action
```

Статусы:

| Status     | Смысл                                                    |
| ---------- | -------------------------------------------------------- |
| `inbox`    | материал сохранён, но требует тега, описания или разбора |
| `saved`    | материал готов к обычному поиску и использованию         |
| `archived` | пользователь спрятал материал из активных сценариев      |

Решение: `inbox` не означает подвешенную запись: material уже сохранён. `status` не заменяет связи с тегами. Истина о тегах живёт в `entryTags`, а `status` ускоряет входящие и пользовательские сценарии.

## Текстовые сообщения

### Сценарий: текст без тега

1. Пользователь пишет: `купить переходник для монитора`.
2. Бот сохраняет entry:
   - `kind: 'text'`;
   - `text: 'купить переходник для монитора'`;
   - `status: 'inbox'`.
3. Бот создаёт `flow: 'tag'`.
4. Бот предлагает:
   - выбрать существующий тег;
   - написать новый тег;
   - оставить во входящие.

### Сценарий: текст с inline-тегом

1. Пользователь пишет: `купить переходник для монитора #покупки`.
2. Бот извлекает `#покупки`.
3. Бот создаёт или находит тег.
4. Бот сохраняет entry и связь.
5. Entry получает `status: 'saved'`.

Тег в базе сохраняется как `name: 'покупки'`, `slug: 'покупки'`; `#` добавляется только при Telegram-отображении.

Inline-парсинг должен находить hashtag-теги в начале, середине и конце текста/caption:

```text
#покупки купить переходник
купить #покупки переходник
купить переходник #покупки
```

Если в сообщении несколько тегов, бот создаёт связь для каждого:

```text
купить переходник #покупки #работа
```

Решение: inline-теги — основной быстрый Telegram-синтаксис, но материал можно сохранить и без них.

## Ссылки

Ссылка — это отдельный `kind: 'link'`, если в сообщении есть URL.

Первый слой:

- сохранить URL;
- сохранить текст/caption целиком;
- тегировать как обычный entry.

Позже:

- canonical URL;
- title;
- description;
- image preview;
- domain;
- duplicate detection по canonical URL.

Вопрос: нужно ли сразу парсить meta? Ответ: нет. Сначала достаточно URL + пользовательского текста. Meta-parser можно добавить без изменения основного lifecycle.

## Фото и изображения

Первый слой:

1. Если есть caption, использовать caption как `description`.
2. Если caption нет, сохранить file metadata, оставить entry `inbox` и создать `flow: 'description'`.
3. Попросить пользователя: `Опиши это фото несколькими словами, чтобы я мог найти его позже`.

Что храним:

- `kind: 'photo'`;
- `telegram.file.fileId`;
- `description`;
- `descriptionSource: 'caption' | 'user' | 'ai' | 'none'`;
- metadata размеров в `telegram.file`, если Telegram отдаёт.

Позже:

- AI-описание 3-7 слов;
- OCR;
- image embeddings.

Решение: мы не обязаны скачивать и хранить изображение у себя, чтобы продукт работал. Для поиска достаточно описания.

---

## Голосовые и аудио

Первый слой:

1. Сохранить Telegram `file_id`.
2. Если пользователь добавил caption/текст рядом, использовать как описание.
3. Если описания нет, попросить ручное описание.

Позже:

- транскрибация;
- краткая сводка;
- извлечение дат и задач.

Вопрос: сохранять ли голосовое без транскрибации? Ответ: да, если есть ручное описание или пользователь готов его добавить. Это позволяет искать голосовые до подключения AI.

---

## Документы и файлы

Первый слой:

- сохранить `file_id`;
- сохранить `fileName`, `mimeType`, `fileSize`, если Telegram отдаёт;
- использовать caption как описание;
- если caption нет, попросить ручное описание.

Позже:

- извлечение текста из PDF/doc;
- AI summary;
- preview;
- поиск внутри документа.

## Пересланные сообщения

Forwarded message обрабатывается по типу оригинального содержимого:

- forwarded text -> `kind: 'text'`;
- forwarded link -> `kind: 'link'`;
- forwarded photo with caption -> `kind: 'photo'`;
- forwarded document -> `kind: 'document'`.

Дополнительно сохраняем forward metadata, если Telegram отдаёт:

- source chat/title/id;
- original sender metadata, если доступно;
- original message date;
- protected/hidden sender state, если доступно.

В текущей schema это кладётся в `telegram.context`. Если Telegram отдаёт больше полей, добавляем их туда типизированно, а не отдельными top-level полями.

Решение: если Telegram скрыл источник, это не ошибка. Entry всё равно сохраняется.

---

## Неподдержанные сообщения

Если тип сообщения пока не поддержан, бот всё равно сохраняет минимальный material:

- `kind: 'unsupported'`;
- `status: 'inbox'`;
- исходный Telegram type в `telegram.type`;
- Telegram metadata в `telegram`;
- `flow: 'description'`, если пользователь может описать материал текстом.

Ответ: `Пока не умею разобрать этот тип. Опиши его несколькими словами, и я сохраню описание.`

Решение: понятный inbox material лучше, чем потеря сообщения. Нормализатор конкретного типа можно добавить позже.

## Текущий слой message types

Реализованный v1 ingestion:

- text сохраняется как `text`, а text с первым URL — как `link`;
- photo, voice, audio, document, video и sticker сохраняют Telegram file metadata;
- caption используется как `description` и проходит через тот же inline-tag parsing;
- media/file без caption создаёт активный `flow: 'description'`;
- следующий text в `description` flow становится `descriptionSource: 'user'`, после чего flow переключается на `tag`;
- новое media-сообщение не заменяет активный flow: бот просит сначала закончить предыдущий материал;
- forwarded и reply metadata сохраняются в `telegram.context`;
- unsupported message сохраняется как `kind: 'unsupported'` и просит ручное описание.

`edited_message` обновляет сохранённый entry по Telegram source key. Обычное удаление Telegram-сообщения не приходит боту как standard update, поэтому пользователь явно архивирует материал через reply `/delete`.

Позже, отдельными слоями:

- AI description для media/file entries;
- transcription для voice/audio;
- search ranking по типу, тегам, описанию, source metadata и свежести;
- group mode с правилами владельца, участников и приватности;
- web-view для reply/forward связей и объединения нескольких сообщений в один material;
- Telegram Business delete updates, если появится business-сценарий.

## Reply на сообщение

Reply может означать два разных сценария:

1. Пользователь отвечает на сообщение бота в рамках текущего `flow`.
2. Пользователь отвечает на уже сохранённый материал и добавляет комментарий/уточнение.

Первый слой:

- текущий `flow` имеет приоритет над обычным entry ingestion;
- если текущего `flow` нет, reply сохраняется как новый entry с metadata `replyToMessageId`;
- если исходное сообщение уже известно системе, можно связать через `relatedEntryId`.

Позже:

- комментарии к entries;
- thread view;
- объединение нескольких сообщений в один материал.

## Тегирование

### Если тегов нет

Бот после первого сохранения без тега:

```text
Сохранил во входящие. Напиши тег в формате #example.
```

Следующее текстовое сообщение становится тегом, если есть текущий `flow: 'tag'` и сообщение содержит один валидный hashtag token.

### Если теги есть

Бот показывает последние теги inline-кнопками и даёт возможность написать новый hashtag-тег.

Первый слой:

- показывать до 8 последних тегов;
- выбор inline-кнопки привязывает тег к активному `flow: 'tag'`;
- новый тег можно написать обычным hashtag-сообщением или создать через `/tag_new #tag`;
- если пользователь ничего не выбирает, материал остаётся во входящих.

Позже:

- популярные теги;
- AI-предложение тегов;
- быстрые команды;
- автодополнение.

## Входящие

`/inbox_count` показывает bounded count по текущему пользователю. Если материалов больше лимита первого слоя, бот показывает `+`, а не делает полный scan.

`/inbox` берёт самый старый `entry` со статусом `inbox`, создаёт для него активный `flow: 'tag'`, показывает короткий preview и inline-кнопки:

- до 8 последних тегов;
- `Пропустить`.

Выбор тега использует общий callback `tag:pick:*`: entry получает связь в `entryTags`, статус становится `saved`, активный flow закрывается.

Если пользователь пишет новый hashtag-тег после `/inbox`, текущий `flow: 'tag'` обрабатывает его так же, как после обычного сохранения материала без тега.

`Пропустить` закрывает активный flow, но оставляет entry в `inbox`. Это важно: skip не архивирует материал и не помечает его разобранным.

Если входящие пустые, бот отвечает:

```text
Входящие пустые.
```

## Команды

Базовые команды:

| Команда        | Назначение                                 |
| -------------- | ------------------------------------------ |
| `/start`       | регистрация и onboarding                   |
| `/help`        | справка                                    |
| `/tags`        | список тегов                               |
| `/tag_new`     | создать тег                                |
| `/tag_rename`  | переименовать тег                          |
| `/tag_delete`  | удалить тег                                |
| `/delete`      | убрать material через reply                |
| `/inbox`       | разобрать следующий inbox-материал         |
| `/inbox_count` | показать количество материалов во входящих |
| `/search`      | поиск по text, `#tag`, `type:<kind>`       |
| `/pro`         | выбрать тариф и получить ссылку на оплату  |
| `/plan`        | посмотреть текущий тариф и срок доступа    |

Решение: команды нужны как стабильный интерфейс, но быстрые inline-кнопки важнее для ежедневного flow.

### Поиск

Первый search-layer работает без AI и использует общий criteria contract:

- `text` — слова из запроса;
- `tags` — hashtag-фильтры, например `#работа`;
- `kind` — фильтр `type:photo`, `type:document`, `kind:voice`;
- `limit` — ограниченный размер выдачи.

Примеры:

```text
/search договор
/search #работа
/search договор #работа type:document
```

Бот ищет только активные материалы: `inbox` и `saved`. `archived` не попадает в выдачу. Text search в первом слое проверяет `text`, `description`, `url` и компактную file/source metadata. Для больших объёмов позже добавляется full-text/search index и ranking, но текущий contract должен остаться тем же.

## Onboarding и прогресс

Первый `/start` должен не только зарегистрировать пользователя, но и объяснить ближайшее действие: отправь сообщение, а потом выбери или создай тег.

Будущий лёгкий слой мотивации:

- показать, сколько материалов во входящих;
- предлагать разобрать один материал за раз;
- показывать прогресс после тегирования;
- напоминать о несортированном, если пользователь это не отключил.

Это не отдельная игровая система. Это способ поддержать основной цикл `capture -> tag -> find`.

## Idempotency

Telegram может прислать повторный update или handler может быть перезапущен.

Правило:

- уникальность entry для Telegram source определяется через `userId + sourceChatId + sourceMessageId`;
- повторная обработка не создаёт новый entry;
- если первый проход успел создать entry, но не успел создать `flow`, повторный проход должен восстановить недостающий следующий шаг.

Это один из критичных сценариев для тестов.

## Bot events

`botEvents` — простой append-only журнал жизнедеятельности бота. Это не продуктовая история материалов и не analytics warehouse; это первый рабочий слой, чтобы видеть, кто что делает и где handler отклонил или сломал сценарий.

Поля:

| Поле          | Смысл                                                    |
| ------------- | -------------------------------------------------------- |
| `userId`      | ссылка на `users`, если уже известна                     |
| `telegramId`  | Telegram user id для событий до регистрации              |
| `chatId`      | Telegram chat id                                         |
| `chatKind`    | `bot`, `group`, `supergroup`                             |
| `source`      | пока `telegram`                                          |
| `kind`        | `command`, `message`, `flow`, `entry`, `error`, `system` |
| `action`      | короткое действие: `start`, `help`, `text`, etc.         |
| `status`      | `ok`, `ignored`, `rejected`, `error`                     |
| `command`     | команда, если событие командное                          |
| `messageKind` | тип сообщения, если событие связано с сообщением         |
| `entryId`     | связь с entry, когда entry уже создан                    |
| `flowId`      | связь с flow, когда flow уже создан                      |
| `context`     | компактные детали: update/message id, length, reason     |
| `createdAt`   | timestamp записи события                                 |

Что пишем в первом слое:

- `/start` и `/help`;
- текстовые сообщения;
- команды, пришедшие как обычный `message:text`;
- rejected-сценарии: invalid context, bot account, not registered, group/private-only позже;
- handler errors и unhandled grammY errors.

Что не пишем:

- полный текст сообщения;
- токены, env, payload с секретами;
- большие Telegram update objects.

Решение: `botEvents` хранит компактный факт действия. Полный debug payload при необходимости можно добавить позже отдельным short-lived debug layer, но не смешивать с основным журналом.

### Daily metrics

`user_metrics_daily` пока не добавляем. Это будущая денормализованная агрегация поверх `botEvents` и продуктовых таблиц.

Потенциальные поля:

| Поле             | Смысл                              |
| ---------------- | ---------------------------------- |
| `userId`         | пользователь                       |
| `day`            | день в формате `YYYY-MM-DD`        |
| `commands`       | количество команд                  |
| `messages`       | количество сообщений               |
| `entriesCreated` | созданные entries                  |
| `entriesTagged`  | entries, получившие тег            |
| `inboxCreated`   | материалы, оставленные во входящих |
| `errors`         | ошибки handler/use-case            |
| `lastActivityAt` | последняя активность в этот день   |
| `updatedAt`      | timestamp обновления агрегата      |

Добавлять её стоит, когда появится реальная потребность в графиках, лимитах, streaks или дешёвых dashboard-счётчиках. До этого `botEvents` достаточно: он проще, честнее и не требует решать cron/backfill раньше времени.

## Редактирование и удаление

`edited_message` синхронизируется с уже сохранённым entry по ключу `userId + sourceChatId + sourceMessageId`.

Что обновляется:

- `kind`;
- `text` или `description`;
- `descriptionSource`;
- `url`;
- inline-теги и связи `entryTags`;
- Telegram metadata.

Если после редактирования у материала нет тегов, он возвращается в `inbox`. Если после редактирования media/file снова требует описания, бот создаёт `flow: 'description'`.

Обычное удаление Telegram-сообщений не приходит боту как update в стандартных personal/group чатах. Bot API отдаёт delete updates только для connected business-сценариев. Поэтому для запуска используем явное удаление:

1. Пользователь отвечает `/delete` на исходный материал.
2. Бот находит entry по `userId + sourceChatId + replyToMessageId`.
3. Entry получает `status: 'archived'`.
4. Если по нему был активный flow, flow становится `cancelled`.

## Тестовая стратегия

### Что тестировать автоматически

- normalizer для каждого message type;
- извлечение URL;
- извлечение inline-тегов;
- обработку flows;
- выбор следующего reply;
- idempotent save;
- создание и привязку тегов;
- inbox transitions;
- fallback для unsupported messages.

### Что не тестировать unit-тестами

- реальный Telegram network;
- реальный long-polling;
- визуальный вид inline-кнопок в Telegram client;
- внешние AI API.

### Подход

- Для bot-flow и pure-логики использовать TDD: сначала meaningful failing test, затем реализация.
- Convex v1 тестировать fake-first через adapter/service слой.
- Реальные Convex functions защищать validators, typecheck/codegen и helper-тестами.
- Для каждого bot-slice держать manual smoke checklist: `/start`, текст с тегом, текст без тега, media без caption, создание первого тега, `/inbox`, edit сохранённого сообщения, reply `/delete`, private-only ответ в группе.

### Рекомендуемая структура

```text
apps/bot/src/
├── bot/
│   ├── handlers.ts
│   ├── messages.ts
│   └── flow.test.ts
├── telegram/
│   ├── normalize.ts
│   └── normalize.test.ts
├── entries/
│   ├── flow.ts
│   └── flow.test.ts
└── convex/
    ├── client.ts
    └── fake-client.test.ts
```

Позже pure-логику можно перенести в `packages/domain` и `packages/telegram`, когда она стабилизируется.

## Открытые вопросы с выбранными ответами

**Нужно ли сейчас делать полноценный web-кабинет?** Нет. Сейчас фокус на боте. Web нужен позже для просмотра, публичных страниц и удобного управления.

**Нужно ли сразу делать AI?** Нет. Сначала ручные описания. AI подключается как автоматизация уже существующего шага.

**Нужно ли сохранять фото/голосовые/файлы без описания?** Технически можно, но продуктово они почти бесполезны для поиска. Поэтому сохраняем metadata, оставляем entry `inbox` и просим описание через `flow: 'description'`.

**Нужно ли требовать тег перед сохранением?** Нет. Сначала сохраняем, потом тегируем. Иначе пользователь может потерять мысль.

**Нужно ли поддерживать несколько тегов сразу?** Да. Материал может иметь несколько тегов. Первый интерфейс добавляет их по одному: пользователь выбирает тег, затем нажимает `Добавить ещё тег` или `Готово`.

**Какой формат тегов используем?** Только Telegram hashtag-style: `#example`, `#покупки`, `#project_ideas`. `#` не хранится в базе; `name` и `slug` сохраняются без решётки.

**Нужно ли хранить Telegram message text?** Да. Это основа поиска и preview. Privacy mode можно добавить позже.

**Что делать, если пользователь во время flow присылает новый материал?** Первое решение: если есть текущий `flow`, следующий текст считается ответом на него. Если пришёл media/message другого типа, бот уточняет, завершить ли предыдущее действие или сохранить новый материал. В первом слое можно ответить: `Сначала закончим с предыдущим материалом: напиши тег или нажми Оставить во входящие`.

**Что делать с удалением тегов?** Удалять тег и связи, но не материалы. Материалы без оставшихся тегов возвращаются в `inbox`, если не archived.

**Что делать с группами в v1?** Не сохранять материалы из групп. Бот коротко объясняет, что пока работает только в личном чате.

**Что делать с `edited_message` и удалением Telegram-сообщений?** `edited_message` обновляет сохранённый entry. Авто-sync обычного удаления невозможен через Bot API, поэтому пользователь удаляет entry явно: reply `/delete` на исходный материал.
