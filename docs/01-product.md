# Product — Bardak

Bardak — Telegram-first продукт для личного цифрового пространства. Пользователь отправляет в бота мысли, ссылки, пересланные сообщения, фото, голосовые, документы и другие материалы, а бот помогает сохранить их с понятным описанием, разложить по тегам, найти позже и собрать в удобные подборки.

Главный принцип: пользователь не должен уходить из Telegram, чтобы поддерживать порядок. Web-интерфейс нужен как дополнительный слой для просмотра, редактирования, поиска и шеринга, но первичная ценность живёт в боте.

---

## Зачем продукт существует

У активного пользователя Telegram часто есть личный хаос: «Избранное», приватные каналы, заметки самому себе, пересланные посты, скриншоты, чеки, идеи, голосовые мысли, ссылки и документы. Всё это легко сохранить, но трудно найти и использовать.

Bardak решает не задачу хранения как такового, а задачу превращения хаоса в рабочую личную базу:

1. Быстро сохранить материал.
2. Добавить тег или отложить сортировку.
3. Дать короткое описание для материалов без текста.
4. Найти сохранённое по тегу, тексту, типу и смыслу.
5. Собрать материалы в страницу или подборку.
6. Поделиться подборкой ссылкой.

---

## Продуктовый фокус

Мы не делаем временную демку ради галочки. Мы строим полноценный продукт маленькими проверяемыми слоями. Каждый слой должен:

- давать пользователю рабочую ценность;
- не ломать уже сохранённые данные;
- оставлять понятный путь для расширения;
- покрываться тестами там, где поведение можно проверить без Telegram;
- иметь зафиксированный Definition of Done в плане.

Текущий фокус разработки: **Telegram-бот и core data layer**.

Пока web не должен становиться центром разработки. Он нужен для демонстрационных страниц, публичного просмотра и будущего удобного управления, но все ключевые сценарии сначала проектируются как bot-first.

## Сценарии использования

Три режима важны продуктово, но реализуются по очереди:

1. **Личный чат с ботом** — основной текущий сценарий. Пользователь пишет боту напрямую и строит личную базу.
2. **Приватная группа с ботом** — будущий сценарий, где пользователь так же добавляет бота в личную группу или приватный канал.
3. **Командный чат** — несколько участников собирают общую базу, страницы и подборки. Это отдельный будущий слой, потому что там появляются права, авторство и совместное владение.

Первый рабочий контур строится вокруг личного чата. Но data model не должен закрывать путь к группам: у entries всегда есть `sourceChatId`, `sourceMessageId`, владелец и Telegram metadata.

В первой рабочей версии бот сохраняет материалы только в личном чате. Если бота добавили в группу или написали ему там, он коротко объясняет, что пока работает только в личке.

## Основной цикл продукта

Базовый цикл должен оставаться одинаковым для всех типов контента:

1. **Capture:** пользователь отправляет материал боту.
2. **Normalize:** бот определяет тип и приводит материал к единому внутреннему формату.
3. **Describe:** если материал не является обычным текстом, бот получает короткое описание от пользователя или от AI-слоя.
4. **Tag:** бот привязывает один или несколько тегов сразу либо оставляет материал во входящих.
5. **Find:** пользователь ищет по тегу, тексту, типу, дате и позже по смыслу.
6. **Use:** пользователь открывает материал, собирает подборку, создаёт страницу или делится ссылкой.

Именно этот цикл является продуктовым ядром. Новые типы сообщений и AI-функции должны подключаться к нему, а не создавать отдельные сценарии.

## Типы контента

| Тип                   | Что храним сначала                                       | Как улучшаем позже                                      |
| --------------------- | -------------------------------------------------------- | ------------------------------------------------------- |
| Текст                 | Текст сообщения, Telegram metadata, теги                 | Семантический поиск, AI-сводки, автотеги                |
| Ссылка                | URL и текст сообщения/caption                            | Парсинг title, description, preview, canonical URL      |
| Пересланное сообщение | Основной тип оригинала + forward metadata                | Источник, автор, канал, восстановление контекста        |
| Reply на сообщение    | Основной тип нового сообщения + reply metadata           | Ветки контекста, комментарии к сохранённым материалам   |
| Фото / изображение    | Telegram file id + ручное короткое описание пользователя | AI-описание 3-7 слов, OCR, поиск по изображению         |
| Голосовое / аудио     | Telegram file id + ручное описание пользователя          | Транскрибация, краткое содержание, извлечение дедлайнов |
| Документ / PDF / файл | Telegram file id + ручное описание пользователя          | Извлечение текста, AI-сводка, preview                   |
| Неподдержанный формат | Metadata, статус `inbox`, ручное описание пользователя   | Добавление нормализатора конкретного типа               |

Важное решение: если у типа контента пока нет автоматической обработки, бот всё равно может сохранить его как материал с ручным описанием. Это даёт поиск и теги уже сейчас, а автоматизацию можно добавить позже.

## Теги и входящие

Теги — главный способ превратить сохранение в структуру. Входящие — безопасный контейнер для уже сохранённых материалов, которые пользователь ещё не разобрал или решил оставить без тега.

Правила:

- материал можно сохранить без тега, но он получает статус `inbox`;
- в пользовательском тексте это называется «входящие»;
- `inbox` не значит “не сохранено” или “подвешено”: материал уже в базе и доступен для поиска;
- бот должен мягко возвращать пользователя к разбору входящих;
- пользователь сам создаёт теги прямо в процессе сохранения или через управление тегами;
- продукт не поставляет предзаданный список тегов;
- теги в пользовательском интерфейсе имеют Telegram hashtag-формат: `#example`, `#покупки`, `#project_ideas`;
- тег начинается с `#`, не содержит пробелов, поддерживает буквы, цифры и `_`;
- `#` — синтаксис Telegram-ввода и отображения, а не часть сохранённой идентичности тега;
- список тегов принадлежит пользователю;
- количество тегов не ограничивается на уровне продукта;
- архитектура должна поддерживать несколько тегов на один материал через таблицу связей;
- первый UX добавляет теги по одному: после выбора тега пользователь может нажать `Добавить ещё тег` или `Готово`;
- inline-парсинг должен находить теги в начале, середине или конце текста/caption;
- удаление тега не должно удалять контент.

Базовая геймификация строится вокруг входящих: бот может показывать количество `inbox`-материалов, мягко предлагать разобрать их по одному и давать ощущение прогресса “порядок в бардаке”. Это не должно превращаться в отдельную игровую систему раньше времени, но должно быть учтено как будущий слой поверх статусов и счётчиков.

## Поиск

Поиск развивается слоями:

1. **Обычный поиск:** по тегу, тексту, типу и описанию.
2. **Поиск по описаниям:** фото, голосовые и файлы ищутся через ручное или AI-описание.
3. **Семантический поиск:** пользователь ищет не точную фразу, а смысл.
4. **AI-ответы поверх базы:** бот отвечает на вопросы, опираясь на сохранённые материалы.

Первый слой должен быть реализован без AI. Это снижает стоимость, упрощает тестирование и даёт устойчивую базу.

## Web-роль

Web — второй интерфейс, а не замена бота.

Ближайшие задачи web:

- публичные страницы и подборки;
- просмотр сохранённых материалов;
- управление тегами;
- более удобное редактирование страниц;
- диагностика и внутренний db/admin-интерфейс для разработки.
- внешняя web-интеграция как отдельный клиент поверх той же базы Bardak.

Web-фичи не должны диктовать структуру core data layer. Бот, web и будущие AI-задачи должны использовать одни и те же сущности.

Будущий полноценный web-кабинет включает:

- авторизацию через Telegram Login Widget или WebApp initData;
- ленту всех сохранённых материалов;
- фильтры по тегам и типам;
- детальный просмотр материала;
- управление тегами;
- просмотр и редактирование страниц;
- настройки аккаунта и приватности.

Внешняя web-интеграция подключается как отдельный слой после стабилизации bot/core сценариев. Она должна использовать те же Convex-сущности и ownership rules, не заводить параллельную модель entries/tags/pages и не обходить Telegram-first продуктовый цикл.

## Приватность

Приватность — архитектурное ограничение, а не маркетинговая строчка.

Решения:

- Telegram user id, chat id, message id и metadata хранятся для idempotency и связи с источником.
- Текстовые сообщения в основной версии хранятся, потому что без этого нет нормального поиска.
- В первой рабочей версии текст и описания хранятся в Convex без encryption.
- JWT-подписи и `jose` подходят для access-token signing, но не считаются шифрованием содержимого.
- Для файлов по умолчанию храним Telegram `file_id`, а не загружаем файл в своё хранилище.
- Для фото, голосовых и документов сначала можно хранить ручное описание, не содержимое файла.
- В будущем можно добавить privacy mode или encryption layer, где текст/описания не сохраняются, хранятся ограниченно или шифруются отдельно.

## Монетизация

Монетизация не является текущим фокусом разработки, но продуктовые решения не должны её блокировать.

Предпочтительная модель:

| Тариф          | Модель                  | Что включает                                                       |
| -------------- | ----------------------- | ------------------------------------------------------------------ |
| Free           | Бесплатно               | Ограничения по тегам, AI-запросам, страницам или объёму материалов |
| Pro (month)    | Месячная оплата         | Первый платный сценарий для проверки спроса                        |
| Pro (year)     | Годовая оплата          | Альтернатива для тех, кому удобнее оплатить надолго                |
| Pro (lifetime) | Разовая оплата навсегда | Возможный будущий тариф, если подтвердится спрос                   |
| BYOK для AI    | Пользовательский ключ   | Пользователь сам контролирует расходы на AI                        |

Возможные платёжные системы: Telegram Stars, ЮKassa, Stripe или другой провайдер в зависимости от рынка.

Первый планируемый provider для проверки монетизации — YooMoney/ЮMoney. Начальный дизайн зафиксирован в [`05-payments.md`](./05-payments.md): bot-first оплата через короткую ссылку `https://bardak.wzx.cx/p/<paymentId>`, quickpay/form, HTTP-уведомление на `https://bardak.wzx.cx/api/yoomoney/notify`, идентификация по `label` и provider-independent `entitlement`. Доступ пользователя должен храниться provider-independent: payment provider создаёт событие оплаты, а Bardak выдаёт отдельный `entitlement`.

## USP

- **Остаёшься в Telegram.** Не нужно ставить отдельное приложение и менять привычку сохранения.
- **Сохранение превращается в структуру.** Бот не просто принимает материалы, а доводит пользователя до тега, описания или входящих.
- **Описание для нетекстового контента.** Фото, голосовые и файлы становятся searchable даже до AI, потому что пользователь может описать их сам.
- **Страницы и шеринг.** Из личной базы можно собрать красивую подборку и дать ссылку.
- **Приватность и минимум хранения.** Файлы по умолчанию остаются в Telegram, а Bardak хранит metadata, описания, теги и связи.
- **Оплата остаётся простой.** Первый платный flow — ссылка из Telegram и ручное продление monthly/yearly без хранения платёжных данных пользователя.

## Долгосрочные направления

Это не текущий план реализации, а карта будущих слоёв:

- **Search/AI:** AI-описания, автотеги, транскрибация голосовых, OCR, обработка документов, semantic search и AI-ответы по личной базе.
- **Assistant:** «память бота», пользовательские правила, настройка стиля общения, тон ответа и AI-действия поверх выбранных материалов.
- **Organization:** страницы, публичный шеринг, related materials, граф тегов и связей, объединение нескольких сообщений в один material.
- **Inbox/progress:** onboarding, прогресс по входящим, мягкие напоминания, batch-разбор и отключаемые routines.
- **Collaboration:** приватные группы, командные пространства, авторство, ownership и access rules.
- **Web/integrations:** расширенный web-кабинет, публичные страницы, внешняя web-интеграция и внутренние admin/debug views.
- **Business:** YooMoney/ЮMoney payments, provider-independent entitlements, Free/Pro limits, BYOK для AI, возможный lifetime-тариф.
- **Privacy/ops:** privacy mode, encryption layer, audit/debug layer, daily metrics, pino logging и Sentry.
